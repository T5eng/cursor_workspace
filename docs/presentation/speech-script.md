## 【0:03 – 0:15】第一部分：LLM 速览 · Slide 4–6

### LLM 是什么（3 min）

先讲 LLM——Large Language Model，大语言模型。它是今天一切 AI 应用的底层引擎。

LLM **是什么**？简单说，它是一个概率性的文本生成器，同时具备很强的模式匹配和推理能力。你给它一段输入，它根据训练中学到的统计规律，预测下一个最可能出现的 token，一个一个往外吐，最终形成一段看起来很有逻辑的回复。

LLM **不是什么**？这一点很重要。它不是数据库——你问它上个月的用户数，它不知道，除非你把数据喂给它。它不是确定性程序——同样的问题，两次回答可能不一样。它也不是实时知识库——训练数据有截止日期，不知道今天的新闻。

所以它有几个**核心局限**，大家心里要有数：第一，**幻觉**——它会非常自信地说出错误的信息。第二，**上下文有限**——它能「记住」的内容有上限。第三，**成本**——token 是按量计费的，上下文越长越贵。第四，**知识有截止日期**——不联网就不知道最新的事。

理解了这些边界，后面讲 Agent 和 AI Coding 的时候，很多设计选择就讲得通了。

### 五个必懂概念（6 min）

接下来五个概念，是后面所有内容的基石。

**第一个，Context Window，上下文窗口。** 你可以把它理解成模型的「工作记忆」。GPT-4 大概是 128K token，Claude 更长。你的代码、文档、对话历史，全部塞在这个窗口里。窗口满了，早期的内容就会被挤掉——这就是为什么 Agent 会「遗忘」。

**第二个，RAG，Retrieval-Augmented Generation，检索增强生成。** 思路很简单：模型本身不知道你的私有知识，那就先从你的文档库里检索相关片段，塞进 prompt，再让模型回答。好处是不改模型权重，知识可以随时更新。企业里做知识问答、代码库问答，基本都用这套。

**第三个，Function Calling，也叫 Tool Use。** 模型不只会生成文字，还能决定「我现在需要调用哪个外部工具」——查数据库、跑代码、发请求。这是 Agent 能「做事」而不是「说话」的关键能力。

**第四个，System Prompt。** 在每次对话开始前，你给模型设定角色、规则和边界。比如「你是一个资深后端工程师，只输出 TypeScript，不要解释」。好的 System Prompt 是行为可控性的基础。

**第五个，MCP，Model Context Protocol。** 这是 Anthropic 推动的一个开放协议，用来标准化 AI 模型和外部工具之间的连接方式。以前每个框架各自定义工具接口，现在 MCP 提供统一标准——一次开发，Cursor、Claude、OpenClaw 都能用。这是 2025、2026 年非常重要的趋势，后面讲 Agent 和 OpenClaw 的时候会再提到。

### 模型怎么选（3 min）

模型生态大致分两类。

**闭源模型**：GPT 系列、Claude、Gemini。能力强，推理好，开箱即用，按 API 调用付费。日常开发、生产环境，大多数人先用这些。

**开源模型**：Qwen、DeepSeek、Llama 等。可以私有化部署，数据不出内网，成本可控。对合规要求高、或者想跑在自有 GPU 上的团队，这是必选项。

选型的时候，我给你一个口诀：**先定场景和预算，再选模型。** 很多时候，与其花精力换模型，不如把 Context 管理好——精准的 prompt、合适的 Rules、精准的文档引用——效果提升更大。

好，LLM 部分到这里。接下来进入 Agent。

## 【0:15 – 0:30】第二部分：Agent 架构 · Slide 7–9

### 什么是 Agent（4 min）

Agent 是今天分享的第二层。如果说 LLM 是大脑，那 Agent 就是让这个大脑能动手做事的完整系统。

一个标准的 Agent 包含五个组件：**LLM + Planning + Memory + Tools + Feedback**。

Planning 是规划——接到任务后，怎么拆解、按什么顺序执行。Memory 是记忆——短期记住当前对话，长期记住历史经验。Tools 是工具——能调用的外部能力。Feedback 是反馈——执行结果好不好，要不要重试，要不要叫人。

那 Agent 和 Chatbot、Workflow 有什么区别？我列了个对比。

**Chatbot**，比如早期的 ChatGPT 网页版，灵活性低，但可控性高——你问它答，不会乱跑。**Workflow**，比如 Zapier 那种固定流程，灵活性中等，适合重复性任务。**Agent** 灵活性最高，能处理开放任务，但可控性相对较低——它可能做出你没想到的事。

所以 Agent 适合的场景是：任务目标明确，但具体步骤不固定，需要 AI 自己想办法完成。

### 四大组件深入（6 min）

展开讲一下这四个组件。

**Planning，规划。** 最经典的范式叫 ReAct——Reasoning + Acting。Agent 先想一步、做一步、观察结果、再想下一步。比如「修这个 Bug」：先读报错日志，再定位文件，再改代码，再跑测试，失败了再回溯。还有 Plan-and-Execute 模式——先列完整计划，再逐步执行，适合步骤清晰的任务。

**Memory，记忆。** 分两层。短期记忆就是当前对话的上下文，受 Context Window 限制。长期记忆通常用向量数据库——把历史对话、文档、经验 embedding 之后存起来，需要时检索。工作记忆是 Agent 执行过程中的中间结果，比如 Scratchpad，记录当前分析到哪一步了。

**Tools，工具。** 这是 Agent 的「手」。常见工具有：代码执行器、文件读写、HTTP 请求、搜索引擎、数据库查询。设计 Tool 有个原则：**单一职责、描述清晰、错误处理完善**——因为模型是靠 Tool 的 description 来决定调哪个的，描述不清楚就会乱调。

而 **MCP** 在这里扮演重要角色：它让 Tool 的开发和使用标准化。你写一个 MCP Server，暴露文件系统、Git、数据库等能力，任何支持 MCP 的 Agent 都能直接接入。

**Feedback，反馈。** Agent 不是一锤子买卖。执行完要检查结果——测试过了吗？输出格式对吗？不对就重试，或者触发 Human-in-the-loop，让人介入关键决策。好的 Feedback 机制是 Agent 可靠性的保障。

### 框架与 Multi-Agent（5 min）

工程落地的时候，大家常问：用什么框架？

**单 Agent 场景**，LangChain、LangGraph、OpenAI Assistants API 都够用。LangGraph 特别适合需要精细控制执行流程的场景——你可以画一张状态图，定义每个节点做什么、什么条件下跳转。

**多 Agent 场景**，比如 CrewAI、AutoGen，适合角色分工明确的任务——一个 Agent 写代码，一个 Agent 做 Review，一个 Agent 写测试。但多 Agent 带来额外的协调成本和不确定性。

这里有个口诀：**能单 Agent 解决，就别上 Multi-Agent。** 复杂度是实打实的，没有明确的多角色需求，单 Agent 加好 Tools 往往更稳。

最后提一下 MCP 作为新趋势的意义：它正在把 Agent 生态从「各自为战」推向「互联互通」。Cursor 支持 MCP，Claude 支持 MCP，OpenClaw 也支持 MCP。这意味着你写的工具能力，可以在不同 Agent 之间复用——这对团队沉淀工程能力非常重要。

好，Agent 架构讲完了。接下来进入今天最核心的部分——AI Coding 和开源热点。

## 【0:30 – 0:52】第三部分：AI Coding 与开源热点 · Slide 10–15

### AI Coding 演进（3 min）

AI Coding 经历了四个阶段，我把它叫做 L1 到 L4。

**L1，补全时代。** GitHub Copilot 为代表，Tab 键接受建议，AI 帮你写下一行。人还是主导，AI 是副驾驶。

**L2，对话时代。** Chat with Codebase 兴起——你可以 @ 一个文件、一个文件夹，跟 AI 讨论代码。Cursor 的 Chat 模式、Copilot Chat 都是这个阶段的产物。

**L3，Agent 时代。** 这是我们现在所处的阶段。Cursor Agent、Claude Code、OpenAI Codex CLI——AI 不再只是回答问题，而是能自主规划、多文件编辑、跑终端命令、迭代修复。人定义任务，AI 执行，人验收。

**L4，编排自治时代。** 这是 2025 年底到 2026 年最火的方向——OpenClaw、Hermes 这类跑在服务器上的自治 Agent。你通过 Telegram、Slack 发一条消息，它在后台调起 Coding Agent，完成后通知你。7×24 运行，不需要你坐在电脑前。

核心转变就一句话：**从「人写代码、AI 帮」，到「人定义任务、AI 执行、人验收」。**

### 工具三层分工（5 min）

面对这么多工具，怎么选？我把它分成三层。

**第一层，IDE 内嵌。** Cursor、GitHub Copilot、Windsurf。你在写代码的时候顺手用，人机同屏，反馈最快。适合日常开发、局部修改、快速原型。

**第二层，CLI Agent。** Claude Code、Codex、OpenCode。在终端里跑，适合后端工程师、运维、需要批量改文件或跑脚本的场景。优势是能深入项目目录，执行 shell 命令，做大规模重构。

**第三层，编排 Agent。** OpenClaw、Hermes。跑在服务器或 VPS 上，通过 IM 派活，适合自动化流水线、定时任务、Issue 到 PR 的闭环。

这三层不是互斥的，而是**组合使用**。我日常的工作流是：Cursor 里写细节和调试，复杂重构用 Claude Code 在终端跑，重复性的 PR Review 和 Issue 处理交给 OpenClaw 在后台跑。

### 热点一：OpenClaw（7 min）

接下来重点聊两个开源热点。第一个是 **OpenClaw**。

OpenClaw 是什么？它是一个开源的、自治的 AI Agent 框架，MIT 协议。2025 年 11 月由 Peter Steinberger 发布，经历了几轮改名——Warelay、Clawdbot、Moltbot，最终在 2026 年 1 月定名 OpenClaw。GitHub 星标增长极快，到 2026 年上半年已经超过三十万，是开源 AI 项目里增长最快的之一。

但关键不是星标数，而是它的**定位**：OpenClaw 不是代码编辑器，它是**编排层**。

什么意思？你在 Telegram 或 Slack 给它发一条消息：「帮我把 Issue #42 修了，提个 PR。」OpenClaw 收到之后，不会自己写代码——它会通过一个叫 **ACP，Agent Client Protocol** 的协议，调度外部的 Coding Harness，比如 Claude Code、Codex 或 OpenCode。这些 Harness 才是真正读代码、改文件、跑测试的。完成后，OpenClaw 把 PR 链接发回给你。

这个架构的好处是**解耦**：OpenClaw 负责编排、通知、渠道接入；Coding Harness 负责专业编码。你可以换 Harness，也可以换模型——Claude、GPT、DeepSeek、本地 Ollama 都支持。

OpenClaw 还有一套 **Skills 生态**，叫 ClawHub，社区贡献了一百多个预置技能——从 GitHub 操作、浏览器控制，到智能家居。它的能力闭环很强：能看浏览器页面、读 console 报错、改源码、再刷新验证，这在调试前端问题时特别好用。

典型场景有三个：第一，**Issue 到 PR 自动化**——定时扫 GitHub Issue，自动开分支、实现、测试、提 PR。第二，**自动 Code Review**——有新 PR 时，调 Codex 或 Claude Code 读 diff、跑测试、在 GitHub 上留评论。第三，**跨工具流水线**——查日志、定位代码、修 Bug、部署验证，一条龙。

使用上要注意安全：OpenClaw 的 Gateway 默认跑在本地端口，**不要裸暴露到公网**。它拥有较高的系统权限，生产环境要做好认证、网络隔离和权限最小化。

适合谁？个人开发者、小团队、愿意折腾自动化的工程师。不太适合强合规、需要 SLA 的企业场景——那种更适合托管方案。

### 热点二：Hermes Agent（5 min）

第二个热点是 **Hermes Agent**，由 Nous Research 开源。

Hermes 的定位和 OpenClaw 不同。OpenClaw 强调编排和生态，Hermes 强调**持久记忆和自学能力**。

Hermes 的核心机制叫 **Learning Loop，学习循环**。你给它一个复杂任务，比如「每周五生成一份代码质量周报」。第一次它可能摸索很久，调用多个工具，踩一些坑。但任务成功完成后，Hermes 会自动把这套流程蒸馏成一个 **Skill**——一个 SKILL.md 文件，存在 `~/.hermes/skills/` 目录下，遵循 agentskills.io 开放标准。下次遇到类似任务，它直接加载这个 Skill，速度快、成功率高。而且 Skill 会根据你的反馈持续迭代。

记忆方面，Hermes 做了分层设计：语义记忆、情景记忆、工作记忆。这意味着它跨会话、跨任务都能记住你的偏好、项目上下文、历史决策。你不需要每次都重新解释「我们项目用 pnpm、测试框架是 Vitest」。

和 OpenClaw 做个对比。OpenClaw 的 Skills 来自社区市场 ClawHub，拿来即用，生态丰富。Hermes 的 Skills 更多是自己「长」出来的，越用越贴合你的工作流。OpenClaw 适合快速接入 IM 和 Coding 工具，做自动化流水线。Hermes 适合长期部署，做一个越来越懂你的个人助手。

有一句概括两者区别的话：**Claude Code 是和你一起写代码；Hermes 是你睡了它还在学。**

两者都支持 Telegram、Discord、Slack 等渠道，都支持 200 多种模型，都可以跑在便宜的 VPS 上。不是二选一，而是可以组合——OpenClaw 编排 Coding 任务，Hermes 处理需要记忆和学习的长期工作流。

### 三个实践原则（2 min）

讲了这么多工具，最后落地到工程实践，我提炼三个原则。

**第一，Context 优先。** 在 Cursor 里写好 `.cursorrules` 或 `AGENTS.md`，定义项目规范。用 @ 精准引用文件，而不是把整个 repo 塞进去。好的 Context 比换模型更有效。

**第二，小步验收。** 不要让 Agent 一次改五十个文件。拆成小 PR，每个 PR 有明确的验收标准——测试通过、lint 过、功能可演示。Agent 也需要 Feedback，小步才能及时纠错。

**第三，人机分工。** AI 做 80% 的实现——写样板代码、补测试、改格式。人做 20% 的关键决策——架构选型、安全审查、边界 case。当前阶段，全托管的可靠性还不够，人机协作是最优解。

常见坑快速提一下：上下文过长导致遗忘和成本飙升；Agent 陷入死循环反复改同一个文件——要设最大迭代次数；编排 Agent 权限过大——一定要沙箱和最小权限。

## 【0:52 – 0:59】第四部分：总结与 ASI 展望 · Slide 16–19

### 四句话总结（3 min）

好，进入收尾。四句话总结今天的内容。

**第一句：LLM 是引擎，Agent 是架构，AI Coding 是场景。** 三者是层层递进的关系，不是三个独立话题。

**第二句：工具分三层——IDE、CLI、编排 Agent——按场景组合，不是选一个打倒另外两个。**

**第三句：OpenClaw 代表编排加 Harness 的方向，Hermes 代表记忆加自学的方向。** 这是 2026 年开源 Agent 的两极，都值得关注。

**第四句：当前最优解是人机协作，不是全托管。** AI 很强，但关键决策和验收还是要人来做。

### 行业趋势（1 min）

往近处看，几个趋势已经在发生：上下文越来越长，推理能力越来越强；MCP、A2A 等协议让 Agent 互联互通；行业焦点正从 Chatbot 转向 Agentic 系统——能自主规划、多步执行、跨工具协作。对我们开发者来说，角色正在从「写代码」转向「定义问题、设计验收标准、审查结果」。

### DeepMind 与 ASI（4 min）

最后，我想聊一个稍微远一点、但和今天内容紧密相关的话题。

2026 年 6 月 10 日，Google DeepMind 发布了一份约 60 页的报告，标题叫 **《From AGI to ASI》**，已提交到 arXiv。作者团队包括 Marcus Hutter——通用智能理论 AIXI 的提出者，以及 Shane Legg——DeepMind 联合创始人、AGI 概念的早期推动者。这不是一般的科普文章，而是正经的学术路线图。

报告的核心问题是：**达到 AGI 之后，AI 怎么继续发展？**

它先做了严格定义。**AGI，Artificial General Intelligence**，通用人工智能，指的是在大多数认知任务上，能力接近单个人类中位水平的系统。**ASI，Artificial Superintelligence**，人工超级智能，指的是不仅超越个人，而且超越大规模、高协调度的人类专家团队的系统。注意，AlphaGo 在下棋上超越人类不算 ASI——ASI 要求在几乎所有领域都广泛超越人类。

报告提出了从 AGI 到 ASI 的**四条技术路径**，而且强调这四条路不是互斥的，很可能会并行推进：

**第一条，Scaling。** 继续扩大算力、数据和模型规模——就是我们过去几年的路子，但报告认为这条路 alone 可能不够。

**第二条，算法范式跃迁。** 超越当前 Transformer 架构的新方法——也许是新的注意力机制、新的训练范式、新的推理架构。

**第三条，递归自我改进。** AI 系统参与甚至主导自身的研发——写代码改进自己的训练流程、设计新算法、优化推理效率。一旦这个飞轮转起来，进步速度可能远超人类研发团队。

**第四条，多 Agent 集体智能。** 这不是单个超级模型，而是大量 AGI 级别的 Agent 协作，整体能力超过任何单个节点。报告认为，集体智能可能涌现出超级智能，即使没有任何一个 Agent 单独达到 ASI 水平。

第四条和今天讲的内容关系最近。OpenClaw 编排多个 Coding Agent，Hermes 积累 Skills 和经验，DeepMind 自己也在研究百万 Agent 互联时的行为和安全——Google I/O 2026 上，DeepMind CEO **Demis Hassabis** 说了一句很有意思的话：**「我们正处于奇点的山麓。」** 他的意思是，奇点不是一个瞬间的事件，而是一个我们正在走入的时代——AI 从聊天工具变成能自主行动的 Agent，就是踏入山麓的第一步。

报告还强调，AGI 到 ASI 可能不是「一步跃迁」，而是**一系列持续的社会变革**——科学突破、技术迭代、产业重组，接踵而至。DeepMind 的研究路线也很清晰：先定义 AGI 是什么，再研究怎么让它安全，然后描绘 ASI 之后的世界。同时，他们联合多家机构出资一千万美元，研究大规模多 Agent 系统的安全行为——因为当百万 Agent 在网上协作时，可能出现任何单个 Agent 都不会产生的涌现风险。

对我们工程师来说，这意味着什么？

第一，今天学的 Agent 编排、Tool 设计、MCP 标准化，可能正是 ASI 路径四——多 Agent 集体智能——的早期实践。你写的每一个 MCP Server、每一个 Skill，都是在给未来的 Agent 生态添砖加瓦。

第二，安全与治理不是远虑，是近忧。编排 Agent 的权限控制、多 Agent 交互的可观测性、Human-in-the-loop 的兜底机制——这些现在就要做好。

第三，保持学习。技术迭代的速度在加快，今天的热点 OpenClaw 和 Hermes，半年后可能有新的范式。但底层逻辑——LLM 加 Planning 加 Memory 加 Tools 加 Feedback——大概率是长期有效的。

## 【0:59 – 1:00】Q&A · Slide 20

好，今天的分享到这里。最后留几分钟 Q&A。

我预判三个高频问题，先快速回答：

**AI 会取代程序员吗？** 短期内不会。角色在变——从写每一行代码，到定义问题、设计架构、验收结果。会用 AI 的工程师，替代不会用的，而不是 AI 替代所有人。

**公司代码安全怎么保障？** 几个层面：敏感代码用私有化模型或本地部署；发给云端的内容做脱敏；编排 Agent 最小权限、网络隔离；关键改动必须人工 Review。

**小团队从哪里开始？** 第一步，Cursor 或 Copilot 用起来，写好 Rules。第二步，复杂任务试 Claude Code。第三步，有自动化需求再部署 OpenClaw 或 Hermes。不要一上来就追求全自动。
